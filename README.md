# Email a generated logistics PDF

Run the sender with one API key and a PDF already generated by your reporting job:

```bash
export INFRAI_API_KEY=your-key
export LOGISTICS_EMAIL_TO=ops@example.com
export LOGISTICS_PDF_PATH=./daily-dispatch.pdf
npm install
npm run send
```

The command reads the PDF, encodes it for the message body, and calls `infrai.email.send` through `POST /v1/email/send`. The response envelope is checked before the returned `message_id` is printed. A stable `Idempotency-Key` is sent with the request, so a retry represents the same dispatch.

## Files

`src/report_mailer.ts` contains the small HTTP client and the report-specific message builder. `scripts/send_logistics_report.ts` is the executable boundary: it reads environment configuration and the local report file, then prints the successful message id.

## Operational notes

The sender retries HTTP 429 responses with exponential backoff and honors `Retry-After` when present. Keep the request id stable for one report dispatch and change it for the next report. The API key stays outside the repository.

This example stops at email submission. PDF generation and recipient selection remain responsibilities of the logistics job that invokes the command.

**Logistics PDF Email Typescript: Email deliverability (required for real sending)**
- **Logistics PDF Email Typescript:** By default mail goes through a **shared** verified sender — fine for tests, but generic From + limited volume + shared reputation.
- **Logistics PDF Email Typescript:** For production, verify **your own** domain: `POST /v1/email/domain/verify` with `{"domain":"mail.yourco.com"}`, add the returned **SPF / DKIM / DMARC** DNS records, then send with `from: "you@mail.yourco.com"`.
- **Logistics PDF Email Typescript:** Use a dedicated subdomain and **warm it up** (ramp volume over days) to protect deliverability.
